Three purchase records can reproduce an old answer, correct an old calculation,
or calculate with a different reference snapshot. Those are separate questions.
This exhibit runs the same implementation that its fixture tests exercise.

Start with the original interpretation, then select the corrected parser. Hold
both time controls still while changing the reference snapshot. The EUR record
stays unchanged; the two SEK records do not.

<ThreeClocks />

## What each selection means

**Valid time** asks when an assertion applies to the purchase amount. **Record
time** limits the assertions available to this system. The cutoff includes an
assertion recorded at exactly that instant. Among assertions applicable at the
chosen valid time, the latest recorded one takes priority.

**Interpretation version** selects the parser, retained reference snapshot and
rounding policy together. It is a versioned computational basis, rather than a
third chronological ordering. New code can interpret old records, and doing so
does not recreate the calculation that was originally made.

The initial payloads and reference rates come from the synthetic example in
[Schema on split](/notes/schema-on-split/). The temporal history is an
additional fictional case:

- The initial assertions are valid from **2026-05-01 00:00 UTC** and recorded at
  **2026-05-02 09:00 UTC**.
- A p-101 amendment to SEK 15.00 is valid from **2026-05-04 00:00 UTC** and
  recorded at **2026-05-05 09:00 UTC**.
- A p-101 correction to SEK 10.00 applies to the valid interval **[2026-05-01
  00:00 UTC, 2026-05-04 00:00 UTC)** and is recorded at **2026-05-08 09:00
  UTC**. It does not replace the later valid period.

The original parser deliberately retains the decimal-comma defect. Replaying it
establishes what that implementation calculates from the retained inputs. It
does not establish that the amount was economically correct. Conversion uses
integer hundredths and rational rates, with half-up rounding per record before
the total is added.

## Lose the history

The overwrite control keeps only the latest assertion for each record. It keeps
a marker that earlier payloads were discarded, but does not retain their values
in the simulated store. An earlier query therefore reports **Unavailable** and
withholds the total. It does not substitute the current value or sum only the
records it can still answer.

Returning to retained history restores the original fixture store. This is a
reversible demonstration of information loss, not a recovery procedure for a
database that has actually discarded its history.

## What the checks establish

The fixture carries independently specified expected cents and selected
assertions. The implementation reads only its inputs; it does not read the
expected results. Unit checks cover the original published amounts, record-time
and valid-time boundaries, late correction, reference substitution, and lost
history. Deliberately wrong cutoff, parser and snapshot choices fail the
corresponding expectations. The browser check changes controls and checks the
displayed amount, selected assertion and interpretation labels together.

These checks establish agreement for these synthetic cases. They do not
establish a production reporting system or correctness over arbitrary histories.
The model covers nonnegative purchase amounts, three retained records, and a
declared assertion precedence rule.

Bitemporal history is established work. Martin Fowler's
[Bitemporal History](https://martinfowler.com/articles/bitemporal-history.html)
explains the valid/record distinction and its lineage in Snodgrass and SQL:2011.
The additional control here makes the interpretation basis explicit; the exhibit
makes that bounded claim executable.
